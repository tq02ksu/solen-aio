```md
# AGENTS.md

## Project Overview

- `solen-aio` is a split frontend/backend IoT repository.
- `backend/` contains the Java services and protocol/server code.
- `frontend/` contains the web management UI.
- Treat the repo as two distinct applications that happen to live in one repository.

## Repository Map

### Backend

- `backend/pom.xml`: Maven multi-module root.
- `backend/solen-app`: business application, REST API, auth, persistence, scheduled jobs, and server bootstrap.
- `backend/solen-server`: protocol, packet encode/decode, Netty transport, connection handling, and device event abstractions.
- `backend/solen-conch-server`: additional backend module; inspect before changing because it is not described by the root README.
- `backend/solen-server-demo`: demo/example module; avoid changing unless the task is specifically about demo behavior.

### Frontend

- `frontend/package.json`: frontend entry for scripts and dependency constraints.
- `frontend/src/pages`: routed page implementations.
- `frontend/src/components`: shared UI components.
- `frontend/src/store`: Redux state slices.
- `frontend/src/api`: API request wrappers.
- `frontend/src/locales`: i18n strings.

## Working Rules

### Backend Rules

- Put API and business logic changes in `backend/solen-app` unless the task clearly requires protocol or transport changes.
- Put message protocol, Netty pipeline, and low-level device communication changes in `backend/solen-server`.
- Do not spread one feature across multiple backend modules unless the behavior truly crosses those boundaries.
- Prefer the smallest correct edit; this repo already has module boundaries, so use them.
- Treat `backend/solen-app/src/main/resources/application.yml` as sensitive because it contains example tenant credentials and JWT settings.

### Frontend Rules

- Follow the existing stack: React 16, Redux, redux-thunk, react-router-dom v4, and ICE Design Pro conventions.
- Do not introduce modern React-only patterns, framework migrations, or TypeScript conversions unless explicitly requested.
- Preserve existing route, locale, and store organization.
- Keep styling changes aligned with the existing SCSS/module SCSS structure.

## Verification

- Use the narrowest command that proves the change.
- For backend changes in one module, prefer module-scoped Maven verification first.
- For broader backend changes, run `./mvnw test` from `backend/`.
- For frontend changes, use `npm run lint` and `npm run build` from `frontend/`.
- Only run `npm install` when dependency changes are required and lockfile updates are intentional.
- Do not claim success without running relevant verification commands.

## Sensitive Areas

- Do not overwrite credentials, JWT secrets, tenant config, or other environment-like values without explicit instruction.
- Do not rewrite the frontend architecture just to make a local feature easier.
- Do not combine protocol-layer backend work with unrelated UI cleanup in the same change.
- Do not update lockfiles, generated files, or demo modules unless the task requires it.

## Git And Change Scope

- Never discard or overwrite user changes you did not make.
- Keep changes tightly scoped to the requested task.
- Do not commit unless the user explicitly asks for a commit.
- If the worktree is dirty, work around unrelated changes instead of reverting them.

## Agent Workflow Expectations

- Read the relevant module before editing.
- Confirm whether the task belongs to backend, frontend, or both.
- Prefer small diffs over cleanup-driven rewrites.
- Verify before reporting completion.
```
